### Commit

### What it does

A poller runs for the life of the suite, hitting `http://localhost:5173/` every
three seconds. On the first failure it prints one line naming the server and
writes `server-watch.log` with the last successful response, the first failure
and its error, and whether the server ever came back.

The timer is `unref()`d so it cannot hold the process open, the whole start is
wrapped so a broken watcher goes quiet rather than failing global setup, and the
stop function is returned from `globalSetup` for teardown.

### Verification — R4, both halves

**A healthy run stays silent.** This is the half that matters most: a monitor
that cries wolf gets ignored within a week.

```
$ npx playwright test --project=product e2e/smoke.spec.ts
  1 passed (15.7s)
[SERVER WATCH] — no output
server-watch.log — not written
git status --short — empty
```

**A real death is named within one poll interval.** `drill-audit.spec.ts` was
started and the dev server killed by PID partway through, four tests in.

```
[SERVER WATCH] 🚨 The dev server at http://localhost:5173/ STOPPED ANSWERING!
[SERVER WATCH] Recorded failure state in ...\server-watch.log

$ cat server-watch.log
Last successful response: 2026-08-31T13:57:16.631Z
First failure:            2026-08-31T13:57:19.642Z
Error:                    fetch failed
Came back:                No
```

Three seconds between last-good and first-failure. **The line appears before the
test failures it explains**, which is the entire point — the two prior
occurrences produced 27 and 38 unattributed `ERR_CONNECTION_REFUSED` results and
were read as broad application regressions.

```
$ npm run build      clean
$ npx vitest run     34 files, 217 passed
```

### Notes for review

**Can it tell a stall from a death?** Partly. It records `Came back: Yes` if the
server answers again, so a stall that resolves is distinguishable *after the
fact*. It cannot distinguish them at the moment of the first failure, and it does
not try to. **That is a real limitation of the mitigation**, in the same way that
"the preflight is a gate and not a monitor" is a real limitation of P-1's, and it
is written down so the next person does not over-trust it.

**This does not fix P-7 and does not find its cause.** The cause remains unknown.
What changes is that the next occurrence produces a timestamp and a
last-known-good instead of a wall of connection-refused.

**`server-watch.log` needs no `.gitignore` entry** — the existing `*.log` rule
covers it. Confirmed by a clean `git status --short` after a failure run.

**One readability trap left in place.** Inside `poll()`, the `AbortController`'s
timer is also called `timeoutId`, shadowing the outer one that schedules the next
poll. It is correct — the inner is a block-scoped `const` inside `try`, and the
reschedule assigns to the outer `let` from function scope — but it reads like a
bug and should be renamed the next time the file is touched.
