### Why not T-043's approach

T-043 threaded the note map down through `DrillRunner.run()` into `_score()`,
so `targetZones` was built from the drummer's own notes. That works, but it
changes the scoring path — which is guarded by a six-minute audit, and is the
last place that should acquire a new parameter. It also broke `diagnosis.test.ts`
R-T1, the guard protecting C-7.

This version translates at the MIDI boundary instead: `_handleNoteOn` converts
the drummer's raw note into the canonical one before anything else sees it.
Nothing downstream knows a note map exists. The crosstalk filter, the chick
de-duplication from T-039, the zone comparison in the scoring worker and every
drill's `targetZones` all keep comparing exactly the numbers they always did.

That is also why the audit is *expected* to be unchanged rather than merely
hoped to be: for a default kit, `canonicaliseNote` is the identity function,
which the tests assert directly.

### A cycle this exposed

`utils.ts` imports `MIDI_NOTE` from `midi.ts` to build `DRUM_TYPE_TO_MIDI` at
module evaluation. Making `midi.ts` import the mapping helpers from `utils.ts`
closed that loop and left `MIDI_NOTE.SNARE_HEAD` undefined at import time,
taking two test files down. `MIDI_NOTE` now lives in `src/audio/midiNotes.ts`,
a leaf that imports nothing, and `midi.ts` re-exports it so its many importers
are untouched.

### Why the kit mapper listens to raw notes

It is the one component whose job is to learn what a pad sends, so it cannot
use the canonical stream: an unmapped pad never reaches `onHit` at all, and a
pad being *re*-mapped would arrive already translated into whatever it
currently means. Hence `onRawNote`.
