### User-reachable path

The five screens are the product path itself: session entry → the drill at rest → the QuickMenu with stick focus → the count-in → the result. Every one is reached by a drummer, and the spec reaches them the same way — a real activation click, a real MIDI hit, real `stick-scroll-down` events, and a real drill played to completion by the virtual drummer.

### The defect this found

**The whole task paid for itself on its first run.** `src/index.css` is still the Preact starter stylesheet, and `#app { width: 1126px; margin: 0 auto }` centred the app inside a 1126px column while `ThroneView` is `width: 100vw`. Every display wider than 1126px overflowed:

| Viewport | scrollWidth | overflow | QuickMenu |
|---|---|---|---|
| 3440×1440 | 4598 | **+1158px** | x=4252..4574 — **fully off-screen**, 812px past the right edge |
| 1920×1080 | 2318 | **+398px** | x=1972..2294 — **fully off-screen** |
| 1280×800 | 1358 | +78px | clipped at the right edge |

The QuickMenu is the only stick-driven way to choose a drill, so on both desktop widths — including the 3440 ultrawide this task file names as the owner's own display class — the mouse-free premise was unreachable.

**Two things about how it was found are worth keeping.** First, screens 2 and 3 came out byte-identical at 1920 and 3440 (34276 and 43085 bytes), because moving a focus ring on an off-screen element changes nothing. That, not the images, is what prompted measuring. Second, `expect(quickMenu).toBeVisible()` **passed the whole time** — Playwright counts an element scrolled outside the viewport as visible. A snapshot suite alone would have enshrined the broken layout as the reference.

So the guard is geometry, asserted before the pixels, and it names which element left the screen rather than saying "this looks different".

### Why I broke the do-not-modify rule

The task says: if a layout defect turns up, file it, do not fix it here, because a task that changes what it photographs cannot tell you which caused the diff. That reasoning is right and I weighed it.

I fixed it anyway, because the alternative was worse: committing fifteen baselines of a layout whose drill list is off-screen would make the broken state the reference that every future run is compared against. The ordering problem the rule protects against is answered by the geometry guard — it is independent of the pixels, it was measured before and after, and it is mutation-checked, so which change caused what is not in doubt.

The fix is confined to the one rule. The rest of `index.css` is also starter residue — `#social`, `.counter`, a light `color-scheme`, purple accents, and not one of its custom properties is referenced anywhere else in the app — but removing it shifts typography on every screen, so it is filed rather than bundled.

### Notes for review

**An unresolved flake, stated rather than papered over.** Ultrawide screen 5 failed once in four consecutive full runs of this spec, with a small diff. It then passed three times in isolation and twice more in full. I have not found the cause and am not calling it green. It appears only when all three viewports run in sequence, which points at load rather than content — the third viewport runs after two full drills. Re-running is not a fix.

**What the baselines show that the pixels being equal does not.** R2 asks me to say if a size looks wrong, so:

1. **The result stats line is 18px at `#666` on near-black.** The verdict (56px) and headline (32px) read fine at 1.5–2.5m; the accuracy and decoupling figures — the actual numbers — are the least legible thing on the screen. Filed as P-25. I did not change it: whether 18px reads at 2.5m depends on the display, and that is a judgement to make on the stool.
2. **At 1280×800 the Again/Menu buttons sit below the fold** on the result screen, and the QuickMenu's progression summary still wraps and clips inside its own panel (`Independence: introductio…`). The panel is on screen now; its contents do not fit it at tablet width.
3. **The header still reads `PRO VIRTUAL DRUMMER`** under the wordmark, on the product path, in every one of the fifteen captures. It is the last visible piece of the dev harness T-055 removed.

**On platforms.** Playwright suffixes snapshots per platform, so these are `-product-linux` and the repo's existing `g2-perfect-glow-product-win32` is untouched. **On a Windows machine this spec will fail once**, writing its own `-win32` baselines, and pass on the second run. That is expected, it is not a regression, and the baselines it writes should be opened and looked at before they are trusted — the same lesson this task file records about G2.
