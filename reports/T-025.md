# T-025: The audit's ACCEPTABLE runs aim too close to the GREEN edge

## Defect Summary
The `acceptable` test runs in `e2e/drill-audit.spec.ts` used a constant `-10ms` headroom across all drills, regardless of how tight their passing threshold was. This resulted in flakiness for tighter drills, specifically because the scheduling jitter under load pushed the result outside the GREEN edge.

## File Changes
* `e2e/drill-audit.spec.ts`
  * Modified `derivedEarlyMs` to return `timingWindowMs * 0.5` for the `'acceptable'` scenario instead of `timingWindowMs - CLEARANCE_MS`. This ensures headroom scales relative to the difficulty (window) of the drill, giving tighter drills more proportional room while maintaining the boundary test constraints.

## Verification & Constraints

### Boundary Guard (R3)
The boundary guard `T-018` is confirmed passing. `CLEARANCE_MS` is still 10, which passes `expect(CLEARANCE_MS).toBeGreaterThan(BOUNDARY_EXCLUSION_MS)`. For `acceptable` runs, the distance is `Math.abs(0.5 * windowMs - windowMs) = 0.5 * windowMs`. Since the minimum window is 30ms, the minimum distance is 15ms. `15 > 5` passes easily. 

### Coaching Text Change (R4 & R5)
I acknowledge the change in diagnosis text for the ACCEPTABLE runs: at `0.5 * window` the performance falls below the `0.6` coaching threshold from T-024, reporting "In the pocket." rather than "You're rushing on beats...". I did not tune the offset to bypass this. The RUSHING runs continue to effectively test coaching bounds. 

### dynamics-gate-drill-5 (R7)
`dynamics-gate-drill-5` CAN LOSE ZERO NOTES. Its zero-slack row passed all three times since the 15ms headroom kept all notes safely within the boundary. No pass criteria changes were necessary.
