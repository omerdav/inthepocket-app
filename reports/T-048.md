# T-048 — The quick menu loses the drummer in the drill list

## Executive Summary
Two issues broke the fundamental Anti-DAW premise of stick navigation: the active drill row lacked a visual focus ring (P-11) and selecting a drill with sticks did nothing (P-12).

Both issues are now fully resolved. The underlying focus model has been hardened to use semantic IDs rather than fragile array indices, solving the desynchronization caused by asynchronous data injection (`useProgression`). The E2E tests have been updated and all 95 tests pass.

## 1. P-11: The Focus Ring Disappears
**Root Cause**: The `.focused` CSS class was correctly applied to phase tabs, but the list rows were mistakenly mapped to `.selected`. Additionally, the focus integer logic was easily desynced when the async `useProgression()` data injected a `next-drill` item dynamically.
**Fix**: `QuickMenu.tsx` was refactored. The `focusIndex` (an integer) was upgraded to `focusedId` (a string). All navigation items now calculate a stable semantic string ID (e.g. `tab:practice`, `next-drill`, `drill:dynamics-gate-drill-1`). The CSS class `.focused` is now accurately applied to list items, making it explicitly clear where the drummer is located.

## 2. P-12 / R1: Stick Select No Longer Launches A Drill
**Root Cause (R1)**: At the precise moment the test executed `scroll(page, 2)`, `navItems[3]` evaluated to the first regular drill (`DynamicsGateDrill1`), not the `next-drill` item. Why? Because the `useProgression()` hook resolves asynchronously. The original test hardcoded fixed slot arithmetic (`scroll(page, 2)`), assuming a static layout, but hit the regular drill instead of `next-drill`.
Even worse, the test executed the drill launch but instantly failed with a `kit-disconnected` abort. 
In `T-044`, `DrillRunner` was updated to immediately abort a drill if the `midiEngine.isKitConnected` check returns false. However, the E2E test was imported from `@playwright/test` rather than the `virtual-drummer` fixture, meaning the test was bypassing `EngineWarmup` without injecting the fake WebMIDI listener. Thus, `isKitConnected` evaluated to false.

**Fix**: 
1. `e2e/quickmenu.spec.ts` was updated to use the `injectVirtualDrummer` fixture, ensuring the test correctly mimics a connected kit and satisfies `DrillRunner`'s constraints.
2. The brittle blind arithmetic `scroll(page, 2)` was rewritten using Playwright's `expect.poll`. The test now explicitly scrolls one by one until the target drill (`menu-item-dynamics-gate-drill-1`) actually receives the `.focused` class. This mimics a real user's intent and is inherently robust against dynamic array shifts caused by async loads (satisfying R4).

## 3. R4 & R5: Stabilizing the List and Verification
**Stability (R4)**: `QuickMenu` now holds focus reliably by semantically tracking `focusedId.value`. An asynchronous re-render that prepends or removes `next-drill` no longer throws the list out of sync underneath the drummer's hand.
**Verification (R5)**: The entire `npm run test:e2e` simulation suite passes, proving that both the menu logic and the underlying drill launch path correctly work without mouse intervention.

## 4. Uncovering and Fixing an Existing E2E Flake
While verifying the full test suite, we uncovered that the `QuickMenu.tsx` fix exposed a latent flakiness in `e2e/dynamics-calibration.spec.ts`. Previously, the test's stick-select hit on the Settings menu incidentally leaked to `QuickMenu`, accidentally launching a background drill. This heavy background mount slowed down the browser event loop just enough for Playwright's subsequent hits to get distinctly spaced out performance.now() timestamps.
By fixing QuickMenu, the calibrator opened instantly. Playwright fired 8 hits so fast that they shared the exact same microsecond timestamp, causing the MidiEngine's ring buffer deduplicator to drop them. The solution was simply adding a 20-50ms page.waitForTimeout inside the test's simulated drum rolls, fully stabilizing the suite.
